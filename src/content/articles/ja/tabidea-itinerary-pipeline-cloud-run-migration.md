## はじめに

Tabideaでは、AIを使って旅行の旅程を生成している。

最初はWebアプリ側のAPI処理として旅程生成を扱っていた。小さく始めるにはその形で十分だったし、個人開発としても実装しやすかった。

しかし、実際に作り込んでいくと、旅程生成は単なるAPIレスポンスではなく、時間のかかる非同期ワークフローに近いものだと分かってきた。

AIによる生成だけでなく、入力の整理、外部情報の扱い、保存前の検証、進捗管理、失敗時の扱いなど、複数の処理が関わる。これを短いHTTPリクエストの中で完結させようとすると、どうしても無理が出てくる。

そこで、Tabideaの旅程生成パイプラインを、Netlify Functions中心の構成から、Cloud RunとCloud Tasksを使った非同期ジョブ実行モデルへ移行した。

この記事では、旅程生成ロジックの詳しい中身ではなく、なぜ移行したのか、どのように移行したのか、その過程で何にハマったのかをまとめる。

## なぜ移行したのか

一番大きな理由は、旅程生成を「通常のAPI処理」として扱うのがだんだん厳しくなってきたことだ。

旅程生成は、ボタンを押してすぐに終わるような軽い処理ではない。

ユーザーの入力をもとに、旅行日数や目的地、好み、制約などを考慮しながら、保存可能な形の旅程を作る必要がある。さらに、途中で失敗した場合や、処理に時間がかかった場合でも、ユーザーに状況を返せるようにしたい。

このような処理は、普通のAPIレスポンスとして扱うより、ジョブとして扱う方が自然だ。

移行前は、フロントエンド寄りのAPI処理に旅程生成の責務が寄っていた。最初はそれでも問題なかったが、処理が重くなるにつれて、次のような課題が見えてきた。

- リクエストの寿命に生成処理が引っ張られる
- 途中経過を扱いづらい
- 失敗時の状態を残しづらい
- 再試行やキャンセルの設計が難しい
- 将来的な計測や改善につなげづらい

Tabideaにとって、旅程生成はプロダクトの核である。

だからこそ、場当たり的にタイムアウトを伸ばすのではなく、実行基盤から見直すことにした。

## 移行後の考え方

移行後は、旅程生成を「APIがその場で完了させる処理」ではなく、「状態を持つ非同期ジョブ」として扱うようにした。

ざっくり言うと、構成は次のようになる。

- フロントエンドはNetlifyで配信する
- 生成APIはCloud Runで受ける
- 重い生成処理はCloud Runのworkerで実行する
- APIからworkerへの実行依頼はCloud Tasksで行う
- ジョブの状態や結果はDBに保存する
- secret類はSecret Managerなどで管理する

ポイントは、ブラウザが旅程生成そのものを進めないことだ。

ブラウザは生成ジョブを作成し、その進捗を見守る。重い処理はworkerが担当する。成功したら保存済みの旅程へ遷移する。

この形にすると、ユーザー体験を大きく変えずに、裏側の実行責務を切り分けられる。

## APIとworkerを分けた

Cloud Runでは、API用のサービスとworker用のサービスを分けた。

APIは外部から呼ばれる入口である。生成ジョブの作成、状態確認、キャンセルなどを担当する。

一方で、workerは重い生成処理を担当する。こちらは直接公開せず、Cloud Tasks経由で呼び出す形にした。

この分離はかなり大事だった。

APIは短く終わるべきである。リクエストを受けたらジョブを作り、必要な情報を返す。長い処理をAPI側で抱え込まない。

workerは時間のかかる処理を担当する。途中経過を保存しながら、最終的に保存可能な旅程を作る。

このように分けることで、APIの責務とworkerの責務がかなり見えやすくなった。

## 最初から全部作り直したわけではない

移行では、最初から旅程生成の中身をすべて作り直したわけではない。

まずは既存の生成処理をCloud Run上で動かせる形にし、実行基盤を先に移した。

これはかなり意識したところだ。

旅程生成の品質改善と、実行基盤の移行を同時にやると、問題が起きたときに原因が分かりづらくなる。

生成結果が悪くなったのか、workerの実行が失敗しているのか、DBの状態管理が壊れているのか、Cloud Tasksの呼び出しが失敗しているのか。全部を同時に変えると、切り分けが難しくなる。

そこで、まずは「どこで実行するか」を変えることに集中した。

生成ロジックの詳細は大きく変えず、実行場所と状態管理をCloud Run前提に寄せていった。

## 本番切り替えでやったこと

Cloud Runへの移行は、コードを書いてデプロイすれば終わりというものではなかった。

実際には、アプリケーションコード以外にも多くの作業があった。

主にやったことは次のようなものだ。

- Cloud RunのAPIサービスを作る
- Cloud Runのworkerサービスを作る
- Cloud Tasksのqueueを用意する
- service accountとIAMを整理する
- Secret Managerに必要なsecretを用意する
- DB側にジョブ管理のための変更を入れる
- Cloud Runのdomain mappingを設定する
- `api.tabide.ai` のDNSを設定する
- Google-managed certificateの状態を確認する
- Netlify側からCloud Run APIへつなぐ
- 本番環境でsmoke testを行う

やってみると、移行とはコードだけの話ではなかった。

DNS、証明書、IAM、DB migration、queue、secret、frontend proxyまで含めて、全部が移行だった。

## ハマったこと

移行中はいくつかハマった。

大きなものだけまとめる。

### gcloud CLIのセットアップで詰まった

まず、ローカルのWindows環境でGoogle Cloud CLIのセットアップに詰まった。

インストーラーが途中で止まり、最終的には再起動で解決した。

本質的なアプリケーションの問題ではないが、こういうローカル環境の詰まりも移行作業では普通に時間を取られる。

クラウド移行というと、設計やデプロイの話に目が行きがちだが、実際には手元のCLIが動くかどうかも重要である。

### `.gcloudignore` が必要だった

Cloud Buildに送るファイルを整理するために、`.gcloudignore` が必要だった。

最初は `.dockerignore` があれば十分だと思っていたが、Cloud Buildのアップロード対象はそれだけでは制御しきれなかった。

ローカルの一時ファイルや作業用ディレクトリがアップロード対象に入りそうになったため、Cloud Build用に明示的にignore設定を用意した。

このあたりは地味だが、ビルド時間やセキュリティの面でもちゃんと見ておきたいところだ。

### IAMの境界が思ったより重要だった

Cloud Run API、Cloud Run worker、Cloud Tasks、Secret Managerが絡むと、IAMの整理が必要になる。

APIは公開される入口であり、workerは内部実行用である。Cloud Tasksはworkerを呼び出す必要がある。さらに、各サービスは必要なsecretを読める必要がある。

どれか一つでも権限が足りないと動かない。

逆に、広く権限を渡しすぎるのもよくない。

個人開発でも、Cloud Runを使うならservice accountの役割を分ける価値はあると思った。

### 古いworker revisionが呼ばれていた

一番印象に残っているのは、古いworker revisionが残っていた問題だ。

API側は新しい構成になっていても、Cloud Tasksが実際に呼び出しているworkerが古いrevisionのままだと、古い処理が動き続ける。

これにより、DB側の変更とworker側の処理が噛み合わず、生成が失敗した。

この経験から、health checkだけでは不十分だと分かった。

APIの `/health` が通っていても、実際の生成ジョブが成功するとは限らない。Cloud Tasks経由でworkerまで到達し、最後まで処理が完了するかを確認する必要がある。

つまり、本番切り替えではend-to-endのsmoke testが必須である。

### DB側の制約とruntimeの状態がズレた

もう一つ大きかったのが、DB側の制約とworkerが書き込む状態のズレだ。

worker側では新しい状態を書き込むつもりでも、DB側がそれを許可していないと当然失敗する。

TypeScriptの型だけを見ていると気づきにくいが、DBの制約もアプリケーションの契約の一部である。

特に、ジョブの状態や進捗をDBに持たせる場合、アプリケーションコードとDB schemaは一緒に更新しなければならない。

### DNSと証明書には待ち時間がある

`api.tabide.ai` をCloud Runに向けるときも、すぐにすべてが完了するわけではなかった。

DNSの反映には時間差がある。ローカルではまだ解決できないが、public DNSでは見えていることもある。

Google-managed certificateも、DNS設定後すぐにReadyになるとは限らない。

このあたりは、コードのように即座に結果が返るものではない。

本番切り替えでは、焦って次に進まず、DNS、証明書、health checkを順番に確認する必要がある。

## 移行してよかったこと

Cloud Runへ移行してよかったのは、旅程生成を自然な単位で扱えるようになったことだ。

一番大きいのは、旅程生成を「HTTPリクエスト」ではなく「ジョブ」として見られるようになったことだと思う。

これにより、次のようなことがやりやすくなった。

- 生成中の状態を保存できる
- 進捗をUIに返しやすい
- 失敗状態を残しやすい
- retryや再実行の設計を考えやすい
- APIとworkerの責務を分けられる
- フロントエンドを重い処理から切り離せる
- 将来的な計測や改善につなげやすい

特に、TabideaのようにAI生成を中心にしたプロダクトでは、生成の成功・失敗・時間・品質をあとから見返せることが重要になる。

Cloud Runに移したことで、そのための土台を作りやすくなった。

## 逆に、Cloud Runにすれば全部解決するわけではない

Cloud Runに移したからといって、すべてが自動で解決するわけではない。

むしろ、考えることは増える。

workerのtimeout、Cloud Tasksのretry、IAM、secret、DB migration、ログ、DNS、証明書、デプロイ順序など、見るべきものは多い。

ただし、これは複雑になったというより、もともと存在していた複雑さが見える場所に出てきた感覚に近い。

旅程生成はもともと、単純なAPI処理ではなかった。

それを無理に短いリクエストの中へ押し込めるのではなく、非同期ジョブとして扱える場所へ移した。

その結果、複雑さをより正しい場所に置けるようになったと思っている。

## 今後やりたいこと

今回の移行で、旅程生成の実行基盤はかなり整理できた。

今後は、この土台の上で、生成の安定性や計測、管理画面からの確認を強化していきたい。

たとえば、生成にどれくらい時間がかかったのか、どの段階で失敗しやすいのか、どのような入力で時間が伸びやすいのか、といったことを見られるようにしたい。

ただし、ここはTabideaの核にも関わる部分なので、公開できる範囲と内部で改善していく範囲は分けて考える必要がある。

公開記事では、あくまで「重いAI処理をどう実行基盤に載せたか」を中心に書く。

生成ロジックそのものは、今後も内部で磨いていく。

## おわりに

今回の移行は、単にNetlify FunctionsからCloud Runへ処理を移しただけではない。

Tabideaの旅程生成を、短いHTTPリクエストの中で頑張る処理から、Cloud Run上で動く非同期ジョブへ作り替える移行だった。

やってみて感じたのは、AIを使った重い処理は、早い段階で「これはAPIレスポンスなのか、それともジョブなのか」を考えた方がいいということだ。

小さく始めるなら、最初はAPI処理でもいい。

でも、処理が長くなり、途中経過や失敗状態を扱いたくなり、あとから改善できるようにしたくなったら、それはもうジョブとして扱うタイミングかもしれない。

Cloud Run、Cloud Tasks、DBによる状態管理を組み合わせることで、Tabideaの旅程生成はかなり自然な形に近づいた。

もちろん、移行中にはいろいろハマった。

CLIのセットアップ、ignore設定、IAM、古いworker revision、DB制約、DNS、証明書。

コードだけではなく、周辺の運用まで含めて移行だった。

それでも、旅程生成というTabideaの核を長く改善していくためには、必要な移行だったと思っている。
