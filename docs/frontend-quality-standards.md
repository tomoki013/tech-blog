# Frontend Quality Standards

This document is the repository-level rulebook for contributors and AI coding agents.
Read it before changing UI, pages, routing, content schema, or performance-related code.

## 1. Core Principles

This site prioritizes:

- **Static HTML** — all pages are pre-rendered at build time
- **Fast loading** — minimal JavaScript, lazy images, no unnecessary requests
- **Semantic markup** — correct HTML elements for their intended meaning
- **Accessibility** — keyboard navigable, screen-reader friendly, WCAG AA compliant
- **SEO basics** — canonical URLs, alternate locale links, meaningful titles and descriptions
- **Maintainable content structure** — clear separation of content, data, and presentation
- **Minimal JavaScript** — only add client-side JS when there is a clear, irreplaceable user benefit
- **Minimal dependencies** — every new dependency must justify its weight

## 2. Semantic HTML Rules

- The shared `BaseLayout` renders the single `<main>` element. Page components must not add another `<main>`.
- Use `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, and `<footer>` according to meaning, not visual convenience.
- Use `<article>` for blog articles and project detail pages.
- Use `<section>` only for meaningful, self-contained page sections — not as generic wrappers.
- Every major `<section>` should have a visible heading.
- Prefer `aria-labelledby` on major sections that have an associated heading.
- Keep heading order logical: `h1` → `h2` → `h3`. Do not skip levels.
- Do not choose heading levels for visual size. Use CSS for visual styling.
- Use `<time datetime="">` for all article and project dates.
- Use `<dl>` for labeled metadata such as project status, category, and stack.
- Use `<ul>` or `<ol>` for lists of articles, projects, stack items, or highlights.
- Avoid meaningless wrapper `<div>` elements when a semantic element is more appropriate.

## 3. Link and Navigation Rules

- Link text must be descriptive and make sense out of context.
- Avoid vague labels such as "click here", "more", "こちら", or "詳細".
- External links must include `target="_blank"` and `rel="noopener noreferrer"`.
- Do not wrap an entire card in a single link if the card contains multiple interactive elements.
- Prefer explicit action links such as "Read article", "View work", "View GitHub repository".
- Navigation labels must stay short, consistent, and not crowded.
- Primary navigation: **Home / Articles / Works / About** — do not grow beyond what fits cleanly.

## 4. Accessibility Rules

- All interactive elements must be keyboard accessible and focusable.
- Do not remove visible focus styles.
- Do not rely on color alone to convey status, category, or any other meaning.
- Images must have appropriate `alt` text that describes their content.
- Decorative images should use `alt=""`.
- Icon-only controls (buttons, links) need an accessible name via `aria-label` or visually hidden text.
- Form controls, if ever added, must have associated `<label>` elements.
- Use ARIA attributes only when native HTML is insufficient.
- Do not add ARIA roles or attributes that conflict with native element semantics.
- Lighthouse accessibility score must remain ≥ 0.95.

## 5. SEO Rules

- Every page needs a clear, unique `title` and `description` in its `BaseLayout` props.
- Use canonical URLs on every page.
- Use alternate locale links for Japanese and English page pairs.
- Keep sitemap entries canonical — no duplicate or legacy redirect URLs.
- Each page should have one clear main heading.
- Use meaningful section headings that describe their content.
- Project detail pages should read like mini case studies with real context, not thin placeholder pages.
- Do not keyword-stuff metadata. Keep descriptions natural.
- English metadata must be natural for international readers, not literal translations.
- Lighthouse SEO score must remain ≥ 0.95.

## 6. Performance Rules

- All new pages must be statically generated by default.
- Do not add client-side JavaScript unless there is a clear, user-facing benefit with no static alternative.
- Do not add React.
- Do not add MDX.
- Do not add client-side filtering or search.
- Do not add analytics or external tracking scripts.
- Do not add animation libraries.
- Do not add new dependencies without a documented reason.
- Prefer Astro components and static HTML over JavaScript-driven solutions.
- Keep the JavaScript gzip budget passing (default: 50 KB).
- Keep Lighthouse CI passing on all tracked URLs.
- Use `loading="lazy"` and `decoding="async"` on non-critical images.
- Always set `width` and `height` on `<img>` elements to avoid layout shift.
- Avoid large, unoptimized image assets.
- Avoid CLS (Cumulative Layout Shift) by not inserting dynamic content above the fold.
- Avoid expensive web fonts or third-party embeds.
- If a feature increases JavaScript bundle size or hurts Lighthouse scores, document why it is acceptable.

## 7. CSS and UI Rules

Reuse the existing design tokens. Do not invent a parallel visual system.

| Token | Purpose |
|---|---|
| `--color-bg` | Page background |
| `--color-surface` | Card / elevated surface |
| `--color-surface-muted` | Subtle surface, table headers |
| `--color-text` | Primary text |
| `--color-text-muted` | Secondary text, metadata |
| `--color-border` | Borders and dividers |
| `--shadow-soft` | Card drop shadows |

- Keep components responsive. Design mobile-first or ensure mobile works.
- Use spacing and typography consistent with existing pages.
- Avoid heavy animations or transitions. Subtle hover effects are acceptable.
- Respect dark mode. Test all new UI in both light and dark.
- Do not hide important content only visually without accessible fallback handling.

## 8. Content and i18n Rules

- Keep Japanese and English routes consistent: every route at `/path/` must have a counterpart at `/en/path/`.
- Do not ship English pages as low-quality or obviously machine-generated translations.
- Article frontmatter must pass the Astro content collection schema validation.
- `projectIds` in article frontmatter must use valid IDs from `src/data/project-ids.ts`.
- Do not invent project claims, stack details, or achievements.
- If project details are uncertain, use cautious, hedged wording.
- Prefer concise, factual project descriptions over marketing language.

## 9. Security and Privacy Rules

- Never commit secrets, tokens, or credentials to the repository.
- Never expose environment variables in client-side code.
- All external links must use `rel="noopener noreferrer"` to prevent opener access.
- Do not add analytics, telemetry, or third-party tracking scripts without explicit approval.
- Do not collect user data. This is a static portfolio/blog with no user accounts or sessions.
- Do not add forms unless privacy implications and spam handling are designed first.

## 10. Required Checks Before Merging

Run all of the following and ensure they pass:

```bash
pnpm check
pnpm lint
pnpm typecheck
pnpm build
pnpm perf:js-budget
pnpm perf:lhci
```

- Do not merge if any check fails.
- Performance failures must be **optimized first**, not solved by weakening budgets.
- Only adjust Lighthouse or JS budget thresholds if the current environment baseline makes the prior threshold genuinely unrealistic, and document the reason in the config file.

## 11. AI Coding Agent Rules

- **Read this document before changing UI, pages, routing, content schema, or performance-related code.**
- Prefer small, reviewable changes. Avoid large refactors that mix unrelated concerns.
- Do not add dependencies without explaining why and what the impact on bundle size is.
- Do not silently loosen performance budgets or Lighthouse thresholds.
- Do not remove accessibility attributes, ARIA labels, or SEO metadata to simplify implementation.
- Do not implement future phases or features unless explicitly requested in the current task.
- When finalizing work, summarize:
  - Files changed
  - Semantic HTML impact (elements used, heading structure)
  - Accessibility impact (ARIA, keyboard, alt text)
  - SEO impact (titles, descriptions, canonical, sitemap)
  - Performance impact (JS delta, new pages added to Lighthouse CI)
  - Commands run and their results
  - Any failures or unresolved issues
